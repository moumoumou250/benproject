## 全项目 token 消耗审计（产出 docs/token-consumption-audit.md）
- 复测基线（count_tokens + grok/grok-4.6）：`_BASE_TOOLS` 45 只 schema **19,239 tok**；root(deep) 提示词 10,644、child 8,501。每次调用固定载荷：root ≈19.8k、child default 27.2k（44 工具）、exploit 25.0k、sca 24.8k、validate 23.4k、enum 10.5k、recon 9.8k。**schema 比提示词大 2.2 倍**；报告类 6 只 6,308 tok（child 固定成本 23%），其中 create_vulnerability_report 单只 1,978。
- 提示词分段：头部 1,405 / 一~五 2,593 / **六、报告规范 2,234** / 七+root_agent 内联(2.4k)+目录 393+scope 1,085 = 4,446。scope.jinja 单测 1,085 tok，每个 agent 都带。
- 实盘数据（33 会话 / 1,325 条目 / 631,796 tok 历史）：单会话均值 19,145、最大 47,483；工具输出中位 141 / 均值 805 / P90 1,947 / **最大 11,012**；某 run 历史里工具输出占 61~73%，tool_call 参数 25%，reasoning summary 仅 5.6%。
- **新发现（两个口径 bug）**：① SDK `approx_token_count` 用 `bytes/4`，UTF-8 中文低估 20~40%——实测 31KB/9.5k-tok 输出无截断标记穿过 `tool_output_max_tokens=8000`；② `tool_output_max_tokens` 只对 shell 生效，非 shell 工具走 50KB 字节线，同一配置两种含义。
- **顺带确认的缺陷**：`profiles.py` 的 recon/enum `skills=("reconnaissance",)` 是分类名不是片段名 → `SkillNotFoundError` 被 warn-and-skip，这两个 profile 静默拿不到侦察方法论。
- 压缩阈值问题：`maybe_compact` 触发线 = `window - max(20k, output_limit)`，200k 窗口 = **180k 才压缩**，历史可以长到 180k 才动手。
- skills 维度：84 片段 166k tok，均值 1,977（最大 dependency_cve_scanning 4,958）；`create_agent(skills=)` 整篇内联进 child 前缀，3 个 ≈5.9k 常驻。
- 口径纪律（延续既有结论）：schema+提示词在最前段按 ~0.1x 计；`billed ≈ 0.1×Σ上下文 + 1.0×新增`，**轮次是乘数、历史是基数**。故建议分档：一档动压缩阈值/token 计价/截断策略/结论按引用/轮次；二档动工具面（6~8 项，账单只值 10%，理由是无效轮次与指令密度）；三档动 skills 内联与提示词去重。

## 代码执行层对照：sapper vs Ben（产出 docs/code-execution-sapper-vs-ben-v1.md）
- sapper 执行模型：`run_claude()` 调 `claude -p --output-format json --dangerously-skip-permissions`（sapper.py:1427-1502），cwd=挑战目录；命令怎么跑/多久/输出多大全交给 CLI 自带 Bash。三层围栏只有进程级 timeout 600s（:4492）、run 级 `--minutes 10`（:3758）、step 级 max_steps/max_explore，**无单命令超时**。一 intent 一进程，结果只回 1 个 JSON（title+一句 description+doc 落盘），doc 不注入（render_graph_text 只给 70~90 字摘要，:1118-1182）。watchdog `--continue` 重启（watchdog.sh:289/380）。
- Ben 真实执行路径：`_wrap_exec_command`(factory.py:834) → tty 假 → `_run_one_shot_shell`(:789) → `timeout_s = yield_time_ms/1000` → `session.exec` → docker `kill_on_timeout=True`(docker.py:587-631)。**yield 兼作 kill**：SDK 默认 10s、PTY 上限 30s（pty_types.py:11）。超时清理靠 `pkill -f '<完整命令行>'`（docker.py:517-530），长命令/heredoc 常匹配失败留孤儿。工具描述只说"输出会丢"未说"已被杀"（factory.py:753-759），误导模型。
- 实盘 15 runs/392 calls/173 exec：exec 占 44%；**12.1% 超时**；61.3% 命令含 `&`；27.2% 另起一轮读日志；28.3% heredoc；平均 934 字符/最长 4374；tty/workdir/write_stdin 全 0 使用；显式 max_output_tokens 仅 2 次；输出 p50 97/p90 1838/max 10650 tok。
- 方案分档：P0-1 解耦 timeout_s（默认 60、上限 600）+ P0-2 容器内 `timeout -k 5 N` 包裹（整组杀、exit=124）+ P0-3 job 句柄工具（list/output/kill，setsid+pid+exit 文件，扫描器命令 auto 转后台）；P1 结果信封化（exec 专用 400 行/12KB + 摘要指针）、持久 shell（opt-in+PTY 探测）、批量 cmds；P2 命令级 exec.jsonl、per-intent 时间盒、run 末清理。验收：超时率 12.1%→<3%、后台率 61%→<35%、读日志 27%→<10%、输出 p90 1838→<800。
- 不抄 sapper：tmux pane 执行单元、`--dangerously-skip-permissions` 外包、完全无单命令超时（一条 nc 吃满 dispatch）。
