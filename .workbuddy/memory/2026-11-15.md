## 对比分析了 sapper-v2 与 BenProject 的运作机制

- sapper-v2：军团/战役层。指挥官（claude TUI，每 60–120s 读 board）+ tmux 内独立 worker 进程（上限 8 pane）+ watchdog 纯脚本保活；记忆是磁盘 `.sapper/` 事实图（fact/intent DAG，跨会话跨进程）；约束是 8 小时时间预算 + 模型分层（glm 旗舰 / ds-flash）；交付物是旗子（平台记分）。
- BenProject：单次任务层。root agent 纯编排 + 同进程 asyncio 子 agent（共享一个 Docker 沙箱）；记忆是 run 级 threat_model（save/amend）+ notes + coverage + mailbox；约束是 MAX_AGENT_TURNS / token 预算 + 代码级白名单只读闸门；交付物是 report_*.md + trace_*.json + SARIF。
- sapper 的"侦察兵"= 决策型侦察（triage recon）：`worker.sh spawn <code> --p --minutes 4`，flash 模型，产出 service/version/tech/入口 facts + easy/medium/hard 判定，peek 后 kill，按 4.6 升级表派 soldier/general。是信息收集，但目的是"花最少的 token 买一个派兵决定"，不做测绘也不出报告。
- Ben 里的对应：侦察不是独立角色/进程，而是子 Agent 的一个职务 —— root 必须先 `create_agent(skills=["reconnaissance/asset_discovery" | "frontend_contract" | "infrastructure_lifecycle"])`（system_prompt.jinja `<root_agent_directive>`，tests/test_root_prompt_policy.py 强制）；产物写 threat_model/notes/coverage；方法论在 `Ben/skills/reconnaissance/` + `scan_modes/deep.md` Phase 1 + `tooling/` 片段。
- 差异要点：Ben 没有 sapper 那种"探路预算"机制（只有轮数/总预算），也没有难度分级驱动的分派表；反过来 Ben 的 threat_model amend 归属 + coverage needs_follow_up 更适合出报告对账，sapper 的事实图更适合跨会话接力。

## Ben 的信息收集通道（细查代码后）

- 组织：root 不亲自侦察，`create_agent` 派侦查子 Agent（同进程 asyncio，共享一个沙箱）。
- 知识载体：`Ben/skills/reconnaissance/`（asset_discovery / frontend_contract / infrastructure_lifecycle）+ `scan_modes/{quick,standard,deep,blackbox,whitebox}.md` 的 Phase 1 + `tooling/`（13 个 CLI 手册：nmap/httpx/katana/subfinder/naabu/ffuf/nuclei/sqlmap/semgrep/...）。
- 执行通道 4 条：① 沙箱 CLI（镜像内置 nmap+naabu+subfinder+httpx+katana+ffuf+nuclei+gospider+wapiti+sqlmap+semgrep+ast-grep+gitleaks+trufflehog+trivy+vulnx），受 `exec_command` 白名单+只读闸门；② agent-browser（CDP，经 exec_command 驱动）流量自动过 Caido → `list_requests`/`view_request`/`list_sitemap`/`repeat_request`；③ `web_search`/`web_get_contents`（CVE/OSINT）；④ `search_knowledge`（SQLite 向量库，35 篇 md，含 clown-src 攻击面语料）+ `load_skill`。

- sapper 侧对应：侦察兵 `--p --minutes 4`（flash）→ typed facts（host/service/cred/vuln/loot/flag，title/description/doc 三层）→ `sapper recall`；知识是 `sapper kb`（56 条，recon 标签 7 条：Web 信息收集工作流 / 版本指纹方法论 / 字典位置 / git 泄露 / 弱口令清单 ...）；侦察无代码闸门，靠"只打题面容器"的纪律。

## 诊断：为什么 Ben 工具调用多但出不了漏洞（结论已用运行数据核实）

核心断链：子 Agent 的发现从不登记成漏洞报告。
- 9 次 `agent_finish` 全部是 `findings=3~10 filed_reports=0`；23 份 trace/251 次调用里 `create_vulnerability_report` 只出现 1 次；12 次 `finish_scan` 有 11 次是 0 report。
- 根因（代码级）：`Ben/agents/prompts/system_prompt.jinja` 第 310 行的 `{% if report_tool %}`「每确认一项发现立即 create_vulnerability_report 登记」嵌在 247 行的 `{% if is_root %}` 分支内；子 Agent 分支（322 行）只说"你是子 Agent，不输出最终报告，向主 Agent 返回结构化发现"。root 又不能亲自取证（§四 强制取证），于是谁都不登记。
- `agent_finish` 的 docstring 要求"先 create_vulnerability_report 再结束"，但只是文字，无代码校验（`_filed_reports_by` 只用于统计）。→ 建议加硬校验：findings 非空且 filed_reports=0 时拒绝结束。

其余原因（按影响排序）：
1. 元工具吃掉预算：251 次调用里 view_agent_graph 34 / create_agent 29 / wait_for_agents 20 / get_threat_model 16 / save_threat_model 12 / todo 11 / notes 11 / coverage 19 / finish_scan 12 ≈ 65%；真正 exec_command 仅 35 次（14%）。max_turns=12，root 一半轮次在"照镜子"。
2. `wait_for_agents` 阻塞空等：15:06 那次 445s 里 300s 在等（180s+120s 超时）。
3. prompt 自我锁死范围：§二.2「当前阶段只允许低风险只读操作（GET/HEAD 连通性与响应头）」+ §三 第 2 步「漏洞类型矩阵属于后续阶段，当前版本不展开」→ 模型看到 Juice Shop 的 /ftp 200、/encryptionkeys/premium.key 200、/support/logs 200 也只写"未验证，本轮未投放 payload"。
4. 只读闸门连带误伤：`_NET_CLIENT_RE` 覆盖 curl/sqlmap/ffuf/nuclei/httpx/nmap；带 `-d/-F/--json/-T/--post-*`/`-X POST` 一律拒；`_INDIRECTION_RE` 让任何含 `$`/`$()`/反引号的网络命令整条失败（`$` 变量/循环枚举全灭）。
5. 证据门槛「宁可漏报不误报」+ §五 三档分级，与第 1 点叠加 → 什么都进不了"已验证" → 什么都不登记。
6. 有一次纯环境问题：15:06 跑 `http://172.19.0.2`，直连超时/端口 filtered/Caido 502，属靶场没起来，跑了 5 条 needs_follow_up。

修复优先级：挪 jinja 的 report_tool 段到两个分支外（或给子 Agent 单写一段）→ agent_finish 加代码硬校验 → 加 `BEN_STAGE=recon|full` 阶段开关 → 元工具限次（学 sapper 的 `board` 合并成一次）→ wait 超时降到 60s 或改非阻塞 → 给侦查子 Agent 加"探路预算"。

## 修正：preflight 把"未授权"误当成"不可达"（2026-11-15）

- 用户质疑"你确定实现了么"，实测暴露两个真缺陷（不是环境问题）：
  1. `check_target` 里 `if not authorized: return report` —— 白名单外的目标**根本不探测网络**，站点活着也报"不可达"。用户要的是"站通不通"，被授权状态掩盖了。
  2. `_probe_host` 里 TCP 连上但 HTTP 无响应时判 `ok`。在透明代理/TUN 环境下任意 IP 的 connect 都"秒成功"（实测 10.9.9.9:8080 显示 0.000s 连通），会给出假阳性。
- 修法：
  - `TargetReport` 语义拆分：`fatal` 只表示 classify 失败；新增 `authorized`（白名单，skip 视为已授权）与 `ready = reachable and authorized`；`reachable` 只看网络。
  - 未授权继续探测，结论分三态：「可达·已授权」/「可达·未授权（通了也扫不了）」/「不可达」，另有「目标无法识别」。
  - 退出码：0 可达且已授权；1 不可达；2 可达但未授权（改 ALLOWED_TARGETS 即可）。脚本可据此区分补救动作。
  - web 目标 TCP 通但 HTTP 无响应 → 判 FAIL（不再算可达）。
  - 扫描闸门 `check_run_targets`：未授权无条件拦（工具层必拒命令，跑下去白烧额度）；`ready` 全真才放行。
- 测试：`tests/test_target_preflight.py` 25 例全过；含"可达但未授权退 2 且仍做真实探测"、"闸门拦可达但未授权"两例新增。相关回归 44 通过。
- 实测（真实入口 main.py）：本地起服务 → 200/EXIT 0；白名单外 example.com → HTTP 200/EXIT 2；`172.19.0.2` → `No route to host`/EXIT 1（正是之前 5 条 needs_follow_up 的根因）。

## 结论：sapper 的"信息收集"能给 Ben 什么（判断，未改代码）

- 判断轴：sapper 的侦察是**决策型**（4 分钟买一个派兵决定，做完就 kill），Ben 的侦察是**测量型**（asset_discovery 150 行 + tooling 13 个 CLI 手册 + Caido 流量）。"收什么"Ben 已经更厚；sapper 领先的是"收了怎么放、怎么复用、怎么据此派工"。→ 搬组织层，不搬内容层。
- 值得搬三件：①探路预算 + 分级派工（sapper 4.10；`create_agent` 目前无 max_turns 参数，但 `spawn_child_agent` 已接收 max_turns，加一个参数透传即可）；②结构化事实 + recall（notes 已有 wiki/methodology 分类，但没有类型化字段与 engagement 内相似度检索；应复用 Ben/rag 的 SQLite 向量库，别抄 sapper 的 token 重叠打分器）；③"目标输出＝不可信数据"明文（当前只在 tooling/agent_browser.md 提过，system_prompt.jinja 388 行里没有）。
- 不搬：tmux/pane/watchdog（Ben 是进程内 asyncio + 预算停泊 + resume）、arena/flag/实例上限（赛制件）、426 行军规（为 flash 级指挥官写的，Ben 的 prompt 已 388 行且被 tests/test_root_prompt_policy.py 断言）、sapper CLI 子进程做存储（会多出第二套真相与绕过面）。
- 风险：现有 notes / coverage / threat_model 已是三套共享记忆，再加事实图成第四套 → 需单一 hydrate/persist 路径；recall 若跨 run 索引 = 客户数据跨项目保留，必须做成显式开关。
- 排序建议：先修已知断链（report_tool 段位置、BEN_STAGE 阶段开关、元工具限次），再谈侦察组织——否则侦察再规范也不产出漏洞报告。

## 新增 `ben scout` 侦察兵 CLI（时间盒 + 端口/版本/入口面 + 裁定）

- 用户要求"把 sapper 侦察兵那套（service fact / 钉版本 / 技术栈入口面 / easy|medium|hard）做成 Ben 的 CLI"。新建 `Ben/interface/cli/scout.py`（~900 行），**不改** recon.py：`class Scout(Recon)` 继承通道/闸门/指纹/软404基线，只加三步。

- 三处设计判断（写进代码注释，供后人改时别踩）：
  1. **端口**：容器内 nmap `-sT` 先只扫状态，再对已开端口做 `-sV`（分两段，省时间）；无 nmap 退 `nc -z`（只能判通/不通，明说区分不了 closed/filtered）；两者都无则跳过并说明，**不降级到宿主机裸 socket**——那会让闸门看不见目标（`/dev/tcp` 里的 host 带 `/` 被当路径丢掉，是真实绕过面）。

  3. **裁定**：确定性打分（easy/hard 双向 + 每条 signal/weight/toward 可复核），level→next_step 映射 soldier/general/scout-again；全站软 404 时 confidence=low（测量不可信 → 重测，不硬派）。
- 关键坑（真跑出来的）：recon 的 `_DEFAULT_PATHS` 顺序是"泄露优先"，`--max-paths` 一截断，最先丢的恰是 /login/actuator 这些**判定要用**的入口 → scout 用独立的 `_SCOUT_PATHS`（入口面在前）；另外 `--no-ports` 时也必须有 service 事实，所以 `_step_web_service` 无条件把目标 URL 记成一条 `-k service`（否则 sapper 上板没有宿主）。
- sapper 导出规则：软 404/baseline 不导出（会和真泄露混淆）；`技术栈指纹` 跳过（与版本台账重复且没有端口）；入口面拆成每入口一条 note；无 `-d` 的空 fact 丢弃。

## `ben scout` 首轮真机跑完后的 4 个修复（已实测）

目标 `http://117.72.199.2:3000/#/` 实为 **OWASP Juice Shop 20.2.0**。

1. **nmap 在 strix 镜像里根本跑不了**：`/usr/bin/nmap` 是 shell wrapper，真二进制 `/usr/lib/nmap/nmap` 带 file caps（`cap_net_bind_service,cap_net_admin,cap_net_raw=eip`），而 Docker 默认 bounding set `0xa80425fb` **不含 NET_ADMIN（bit12）** → `execve` 返回 EPERM（exit 126，`Operation not permitted`）。`command -v nmap` 还会说有。修法：`_nmap_prefix()` 先真跑 `nmap --version`，失败就 `cp /usr/lib/nmap/nmap /tmp/.ben-nmap`（副本无 xattr）+ `NMAPDIR=/usr/share/nmap`，`-sT` 不需要特权。**不要**用 `--cap-add NET_ADMIN` 绕过（等于给沙箱放权）。修复前 32 个开放端口被报成 0 个。
2. **`-sV` 必须逐端口**：8 个端口一批时，只要有一个 tcpwrapped/filtered，`--host-timeout` 会掐掉整批、连 `Ports:` 行都不输出（32 端口 0 版本）。改成 `--version-light` + 每端口 10s（实测 ssh 0.5s / nginx 6.4s / tcpwrapped 5.3s），上限 `_VERSION_MAX_PORTS=16`，优先级按 `_DEFAULT_PORTS` 顺序。
3. **版本台账分 role**：`ssh/mysql/redis` 等归 `network`，只有 `web` 面的版本才算 `locked`。原实现把 OpenSSH 8.9p1 当成"目标已钉死"，直接给出 `EASY/high → soldier`，而 web 应用完全没识别。
4. **已知应用版本接口**（`_KNOWN_APPS`）：页面标题命中 Juice Shop → GET `/rest/admin/application-version` → `{"version":"20.2.0"}`，把 product+version 一起钉死。这是 kb052"版本必须固定下来"的最短路径。
5. 另修：5xx 端点记为 `error` 类入口（路由存在但处理失败，easy+1）；软 404 与真实命中并存时不再整片否定路径结论（只在没有一条与基线不同时才扣 hard）。
